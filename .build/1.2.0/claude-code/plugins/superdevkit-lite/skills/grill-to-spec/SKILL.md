# Grill to Spec

通过分轮访谈建立共同理解，再整理为可实施、可验收的需求说明。深度来自追问答案的后果、检验假设和消除矛盾，不以问题数量或文档长度衡量。

普通讨论、解释或方案比较默认直接回答；开发中的需求确认或用户明确要求访谈时才进入本技能，访谈本身不授权后续实现。

## 分轮追问

- 先查相关代码、项目文档及已确认决定。能查到的事实自己查；用户描述与实现不一致时说明差异，确认是在描述现状还是提出新行为。
- 将需求组织为有依赖的决策树，区分已确认、待决策、待查事实和范围外事项。从目标用户、真实问题与成功标准开始，再展开方案、行为和边界；不是把这些主题一次性列成问卷。
- 每轮选择前提已确定、影响最大的几个问题，编号并说明为何重要，给出推荐、理由和真实取舍。依赖本轮未回答问题的追问留到后续轮次，不替用户预选答案。
- 等回答后更新决策树：这次决定带来了哪些新问题、否定了哪些旧假设、是否与已有答案冲突？继续追问仍未解决的重要分支，不把首轮得到的功能清单当作访谈结束。
- 对含糊词要求具体含义，对笼统认可追问相关边界。“简单”“自动”“管理员”“实时”不能直接变成验收条件；已明确的内容不重复询问。
- 对方案提出有理由的挑战：为何需要它，是否有更小的解法，替代方案牺牲什么？用具体反例检验答案，避免只替用户补全最初设想。

## 检验重要分支

按本次范围与风险选取场景，回答暴露新问题时继续追问；不机械穷举无关主题。

- 用户路径：谁在什么情况下操作，成功如何反馈，失败、取消、重试与恢复时发生什么。
- 规则与状态：权限、所有权、状态转换、时间和数量边界；涉及共享数据时检验冲突、重复操作或并发的产品语义。
- 约束与代价：兼容性、数据保留或迁移、性能目标、外部依赖和不可逆操作；确认承诺是否可实现。
- 验收与取舍：用正常例和反例确认怎样算对，哪些需求本轮不做，被否决方案为何被否决。

例如“允许取消预约”得到肯定后，还应根据场景追问截止时间、操作者权限、取消后的名额与通知，以及重复取消的结果；不要替用户把这些规则补成默认值。与实际需求无关的示例不引入 spec。

## 产物与完成条件

汇总需求与验收时按需读取 [Spec 格式](references/SPEC-FORMAT.md)，优先沿用项目已有格式。

每轮保留简短的已确认决定、理由、被否决选项和待解决问题。术语澄清与重要取舍及时保留，不强制新建术语表或决策档案。单项需求文档落在 `docs/specs/`；旧路径记录迁移前先提出方案，批准前继续引用原记录，不创建重复正文或删除当前开发内容。

当范围内的重要分支均已解决或被用户明确排除，整理 spec：目标、用户行为、约束、非目标、关键决定及理由、可观察的验收场景、修改范围与验证方式。常规实现细节自行判断，不预写完整代码。有仓库且获准落档时写入 `docs/specs/`；仅讨论、没有仓库上下文或尚未获得文档写入授权时，在回复中给出完整草案。

收束前复述关键决定与边界，让用户确认共同理解；若此前已明确确认同一结论，直接引用，不增加仪式性确认。用户要求提前结束时交付标明缺口的草案，不声称访谈已完成。

完成条件：重要产品决策有确认来源，矛盾已消解，相关正常与异常场景能判断对错，没有被偷偷假设的重要规则。未解决问题只阻塞依赖它的拆票与实现，不阻塞无关调查；已完整确认的需求无需重新访谈。
