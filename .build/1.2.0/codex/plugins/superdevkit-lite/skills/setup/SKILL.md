# Setup

让项目的需求、约束、实施、验证、体验与交付都有明确依据。默认只读检查，在回复中展示具体方案；用户批准本次方案后才修改文档。它用于治理整理，不是每次开发的前置步骤。

## 检查与补缺

- 核对当前仓库、分支与已有改动，从实际治理入口及其引用识别文档职责、作用域和使用中的 harness。按疑点查相关代码、配置、测试与交付记录，记录检查范围；不预先通读整个仓库。
- 完全没有系统级文档时，先查已有代码与产品资料，再调用 [grill-to-spec](../grill-to-spec/SKILL.md) 确认产品目标、用户、范围、约束与验收条件。已有确认结论直接沿用，访谈只补缺口。方案批准前，访谈记录和 spec 草案留在回复中。
- 已有文档时，检查覆盖不足、过时、矛盾、重复和无效指令。能查明的事实自行查；产品意图、规则取舍或重要边界不明时进入访谈，未决项只阻塞依赖它的建议。
- 区分当前实现、已确认目标和待确认建议。代码与约定不符时报告偏差，不能默认改文档来迁就实现；历史决策须核对替代关系，不能仅按文件日期认定有效规则。
- 检查治理入口能否区分讨论与开发、按任务路由；需求是否有可观察的验收条件，开发与交付是否有范围和授权边界，验证是否覆盖适用行为与用户体验，开发回报是否引用统一格式。文档存在不代表检查、门禁或部署已经生效；标明仓库核对、实际验证与未知事项。

## 按需使用模板

七份核心文档固定放在 `docs/` 根目录，名称见下表；编号表示人类阅读顺序，不要求 agent 每次按序通读。产品总览放 01，单项需求与 spec 放 `docs/specs/`。保留项目语言和有效内容，不适用的主题说明理由。模板中的占位说明用有依据的内容替换，未知项保留待确认状态，不填造事实。

| 当前检查或拟修改的内容 | 目标位置 | 模板 |
|---|---|---|
| 对外入口、共享约束、多 harness 加载与路由 | 仓库根目录 | [根目录入口](references/entrypoints.md) |
| 产品目标、用户、场景、范围与成功标准 | `docs/01-product-requirement.md` | [产品需求](references/product-requirements.md) |
| 系统组成、模块边界、依赖和数据流 | `docs/02-architecture.md` | [架构](references/architecture.md) |
| 已确认的重要取舍与替代关系 | `docs/03-decision-log.md` | [精简决策日志](references/decision-log.md) |
| 当前能力、阶段目标、依赖和交付状态 | `docs/04-roadmap.md` | [路线图](references/roadmap.md) |
| 设计依据、交互与体验标准 | `docs/05-ux-ux.md` | [UI / UX](references/ui-ux.md) |
| 环境、实施、工作登记、文档维护与交付 | `docs/06-developing.md` | [开发约定](references/developing.md) |
| 验证选择、运行条件、通过标准与证据 | `docs/07-testing.md` | [测试与验收](references/testing.md) |
| 部署、安全、数据等需要独立维护的主题 | `docs/` 根目录，从 08 起按阅读顺序编号 | [扩展文档](references/extensions.md) |

旧文件名、`docs/spec/` 或其他目录需要统一时，先列原位置到目标位置的映射、编号冲突、全部内容去向及受影响引用，批准后迁移。迁移前继续使用原记录，不用空模板覆盖旧文档，不另留两套可编辑正文。

## 修订方案

优先整理格式、章节和导航，补充缺失内容。保留项目事实、人工内容和已有授权，当前开发相关的需求、架构、约束、计划、问题、状态与证据不得因精简而删除。疑似重复或过时的内容先保留并标明疑点；一般整理授权不包含删减。确需删除非当前开发内容时，另列具体原文、依据与影响，取得明确批准。

| 发现的问题 | 拟修改方式 |
|---|---|
| 缺失或过时 | 用可定位的证据补充现行说明；旧内容标明状态并保留依据，未知的产品决定先确认 |
| 约定与实现、多个文档互相冲突 | 展示冲突双方、来源和影响；确认有效规则，区分文档修订与待实施的代码工作 |
| 重复或职责混杂 | 优先整理章节；经批准再无损合并或迁移，所有独有信息有去向，原入口保留引用 |
| 要求不可验证 | 补充可观察结果、验证入口和运行前提；尚无检查能力则列为缺口 |
| 历史堆积 | 增加摘要和导航；需归档时单独提出方案，保留全文、编号、替代关系和原有引用 |
| 多 harness 入口漂移 | 核实加载机制，集中共享内容；各入口只保留必要差异，不能仅凭链接存在声称会自动加载 |

先交付可审阅的方案：每项指出文件及位置、证据与问题、建议替换文本或 diff、影响和待确认项；新增文件给出完整拟稿，删除、迁移、归档与路由变更明确列出。没有实质问题就说明检查范围和结论，不制造修改。

## 授权修改与完成

获得用户对具体方案的批准后，只实施获准部分。已有批准覆盖同一方案与范围时直接沿用；部分批准只执行对应部分。重新核对文件变化，出现新的冲突或范围扩展时展示补充方案，不覆盖无关改动。治理文档授权不包含安装插件、修改业务代码或运行配置、合并及部署。

修改后对照原文核对内容去向，确认当前开发信息无遗漏，再检查目录与编号、事实依据、文件与锚点链接、阅读路由、跨文档一致性及 diff。对多 harness 分别报告已验证的入口解析或实际加载、未验证的部分；静态检查不能冒充会话实测。说明修改了什么、仍有哪些治理或实现缺口；不把文档齐全称为系统已满足质量标准。
