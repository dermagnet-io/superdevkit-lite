# Spec 格式

整理访谈结论时使用。单项需求与 spec 保存在 `docs/specs/`，文件名可用 `YYYY-MM-DD-<topic>.md`；产品总体需求维护在 `docs/01-product-requirement.md`。已有 spec 保留原有内容和确认依据；旧路径迁移须先提出方案并获批准，之前继续引用原记录。项目有模板时沿用其有效内容，优先整理格式和补缺。没有仓库或未获文档写入授权时在回复中交付草案。模板中的提示替换为实际结论，不为填满章节编造需求。

```markdown
# <需求名称>

状态：草案 / 已确认（选择实际状态）
来源：<用户请求或既有需求的引用>
确认依据：<谁在何时确认了哪些范围；尚未确认则明确说明>

## 问题与目标
<目标用户、当前困难、预期收益及可观察的成功标准>

## 范围与非目标
- 本次包含：<用户能力或结果>
- 本次不做：<明确排除的范围与理由>

## 用户行为与规则
- R1：<谁在什么条件下做什么，系统如何响应>
- <相关权限、状态转换、边界、失败及恢复规则>

## 约束与关键决定
- <兼容性、数据、依赖、体验等适用约束>
- <已确认决定、理由与被否决方案；已有记录用引用>

## 验收场景
| 编号 | 对应需求 | 前提与操作 | 可观察的预期结果 |
|---|---|---|---|
| A1 | R1 | <正常场景> | <明确结果> |
| A2 | R1 | <相关边界或失败场景> | <明确结果及恢复方式> |

## 修改范围与验证
<涉及模块或路径、不可修改范围，以及如何验证验收场景>

## 未决事项
<缺失决定、影响哪些需求或票、解决条件；没有则写无>
```

按任务规模合并章节，但保留目标、范围、约束、验收与确认状态。正常场景通过不代表异常场景可省略；只列与需求有关的场景，不机械补齐所有组合。

已确认内容、建议和未决问题分开写。草案可以保留缺口，但不能标成可直接实施；明确哪个部分受阻。不要预写整套实现代码，也不要把一次性实现选择升级为产品要求。
